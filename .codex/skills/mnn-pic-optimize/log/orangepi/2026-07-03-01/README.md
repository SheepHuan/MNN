# OrangePi 2026-07-03 01

## Summary

- Objective: optimize OpenCL PIC no-repair / decode-repair attention by keeping PagedCache as the source of truth while adding a decode-friendly transposed K view.
- Implemented `SharedPagedCache::decodeKey` with layout `[B, H_kv, D, max_slots]`, allocated together with PagedCache instead of during decode.
- Added one-time `decode_prepare_transpose_k` from row-layout PagedCache K to DecodeK. This is profiled separately and is not counted as decode TPOT in the A/B table.
- Added q=1 fused DecodeK append+attention path and q>1 sparse decode-repair path. q>1 uses a separate sparse append/update kernel, then a DecodeK attention kernel, because repair rows need a kernel-launch boundary before later rows read their updated K/V.
- Fixed PagedCache reuse to accept `maxSlots >= required` so decode does not recreate layer cache when the request shape moves between 4096 and 4608 slots.
- Built OrangePi artifact and ran Qwen3-4B, Llama3.2-3B, and MiniCPM5-1B `ctx512`, `q=1/2/4/6/8`, old row-PagedCache path vs new DecodeK path.
- Result: DecodeK is not a universal default yet. It is clearly faster for Llama q=1/2/4/6/8 and MiniCPM q=2/4/6, modest/mixed for Qwen. Highest-performance serving should select per model/shape/q or keep the path env-gated until an automatic heuristic is added.
- The implemented q>1 kernel is a sparse-row DecodeK kernel, not yet the true q2/q4/q8 small-Q tile kernel with shared K-load across rows from the original target note. That remains the next optimization if the goal is to improve Qwen q=2/q8 and reduce per-row duplicate K reads.
- Follow-up P2 implementation added a q=1 append+readonly micro path behind `MNN_PAGED_ATTENTION_DECODE_TRANSPOSED_K_ATTENTION_ONLY=1`. It separates historical DecodeK prepare, current-token append, readonly attention, and optional rank capture in profile output. Default production routing is unchanged.
- Follow-up P1 hardening records a host-side slot prefix snapshot for DecodeK readiness. Decode now only accepts ready-hit/prefix-stable DecodeK and will not launch `decode_prepare_transpose_k` with `inside_decode=1`.
- A pure q=1 readonly-only micro gate, `MNN_PAGED_ATTENTION_DECODE_TRANSPOSED_K_READONLY_ONLY=1`, runs only when DecodeK already covers `kv_len`; it does not append K/V or prepare in decode.
- Local compile smoke passed for both Rhino/Aidlux and OrangePi OpenCL `MNN_CL` targets.
- Consolidated plan added: keep q=1 default conservative until Rhino fused-vs-append record data is complete; implement q>1 qtile after the two-stage sparse append boundary; promote default routing only after no-regression TPOT across the three target models, both devices, and q=1/2/4/6/8.
- Rhino warmed-cache q=1 record smoke completed for MiniCPM5-1B, Qwen3-4B, and Llama3.2-3B. Result: old/fused/append+readonly are effectively tied on MiniCPM and Llama, while Qwen slightly prefers append+readonly. This supports keeping q=1 routing conservative and device/shape scoped instead of promoting DecodeK globally.
- Warmed Rhino logs were clean: no `ERROR`, no `Cache invalid`, no `target unavailable`, no `decode_prepare_transpose_k`, and no `decode_prepare_inside_decode=1`.
- q=1 hardening follow-up: default `MNN_PAGED_ATTENTION_DECODE_TRANSPOSED_K=1` no longer auto-routes q=1 to DecodeK fused or append+readonly. q=1 DecodeK variants are now explicit opt-in via `MNN_PAGED_ATTENTION_DECODE_TRANSPOSED_K_Q1_ROUTE=fused|append_readonly` or the readonly/attention-only debug flags.
- Added `pic_decode_repair_tokens_per_step` so non-decode setup only prepares DecodeK when actual q>1 decode-repair is active; no-repair q=1 keeps prepare out. A debug Rhino Llama q=1 run confirmed no `decode_key prepare` and no q1 transposed-K route branch, only the old `copy_paged_kv` invalidate.
- route6 q=1 median smoke (`ctx512`, `max_tokens=8`, warm=2, repeats=5) is dominated by device variance on OrangePi, but it validates the control-plane contract: prepare is absent from timed decode and q=1 production remains old identity unless explicitly forced. The optimization focus now moves to q>1 qtile after sparse DecodeK append.
- Added Decode Optimization Plan V2: q=1 old fallback is only a guardrail, not success. Next steps are true old/new attention-only q=1 profiling, then K-vectorized or GQA-cooperative DecodeK q=1 kernels if attention-only loses, then q>1 qtile kernels after the existing sparse append boundary.
- Added Decode Optimization Plan V3 after q=1 new attention-only smoke exposed a harder boundary bug: first decode was still expanding `max_slots=4096 -> 4608` and lazily hydrating a 512-token persistent source segment. The plan now requires an explicit full-reuse decode prepare stage before timed decode: reserve request/source capacity, hydrate all layers, run `decode_prepare_transpose_k` for the logical prefix, then decode may only append current token K/V/DecodeK and run attention/rank.
- Final q=1 route hardening: `preparePagedDecode()` is now called before server decode, and q=1 auto routing is conservative by device/model. Mali only routes Llama3.2-3B to append+readonly DecodeK; MiniCPM5-1B and Qwen3-4B stay on old identity. Adreno routes Llama3.2-3B and Qwen3-4B to fused DecodeK; MiniCPM5-1B stays old. Rebuilt and synced OrangePi/Rhino artifacts after this selector change.
